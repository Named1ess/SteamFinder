# SteamFinder

基于 TypeScript 的 Steam 好友关系探索工具：按层采集好友、持久化缓存、交互关系图、共同好友、最短连接路径、公开资料悬停卡和相关度评分。前端、API、采集 Worker、数据库全部通过 Docker Compose 运行。

## 启动

需要 Docker Desktop（Linux containers）或 Docker Engine + Compose。无需本机安装 Node.js、PostgreSQL 或 Redis。

```sh
docker compose up --build -d
```

打开 <http://localhost:8080>。默认是**公开网页采集模式**：读取公开的 Steam Community 主页与好友页面，不需要 Steam API、密钥或登录。打开页面不会自动采集；输入 Steam 主页或 ID 并点击查询后才会开始。

## 公开网页采集与演示模式

无需申请凭据。可将 `.env.example` 复制为 `.env`，调整网页请求间隔、每日请求预算与本地端口：

```dotenv
STEAM_MODE=live
STEAM_REQUEST_DELAY_MS=2000
DAILY_REQUEST_LIMIT=10000
```

修改配置后应用到服务：

```sh
docker compose up -d --force-recreate api worker
```

输入 `76561199521553744`、`https://steamcommunity.com/profiles/76561199521553744/`，或 `/id/自定义名字` 形式的完整 Steam 主页地址。仅解析公开网页，不读取登录后的页面，也无法读取私密好友列表。网页不可用、受限或结构发生变化时会保留已有结果并标记失败，不会把这些状态当作没有好友。

需要离线体验或运行演示集成验证时，在 `.env` 中显式设置 `STEAM_MODE=demo`，再运行上面的重建命令。演示模式使用本地生成的虚构人物与关系，不访问 Steam。演示数据与公开网页采集的数据分开存储。

## 使用和数据语义

- 默认 2 层、最多 1000 个节点、500 次请求，可调整至最多 3 层、10000 个节点及10000次请求。
- 显示上限独立于采集上限；小范围画面不代表数据库只有这些数据。
- 打开历史记录、刷新浏览器、切换筛选条件只读取数据库。只有新建任务、显式刷新或继续采集会触发采集。
- 任务在后台执行，关闭浏览器不会取消任务。达到预算后可以增加预算并继续；可取消正在进行的任务。
- 好友不可见、请求失败、网页结构不支持、尚未展开分别按不可访问、失败或边界状态标识；未知不等于没有好友。
- 共同好友、路径、社群和排行均基于本次已采集的图。没有找到路径不代表 Steam 上一定不存在路径；深度边界和隐私设置可能造成缺失。
- 连接分析中的起点与终点支持按昵称或完整/部分 Steam ID 搜索，候选项展示完整 ID 以区分重名玩家。搜索覆盖本次保存在数据库中的全部玩家，不受画布显示层级和节点上限限制，也不会触发 Steam 采集。
- 点击刷新会重新查询允许范围内的数据；刷新失败保留之前成功的数据和时间戳。
- 好友关系并非树，重复出现的 SteamID 会合并。SteamID 始终以字符串传输。

## 加载与性能

- 图谱按变化增删节点和连线，保留当前缩放、平移和手动拖动的位置。调整显示人数或层级时保留画面等待数据；浏览器窗口或图谱容器尺寸变化时自动缩放并居中，节点排布保持原样。切换布局或查询时重新布局，也可点击“适应画布”。
- 采集进度优先使用 SSE；连接中断或长时间没有消息时由轮询接管。重复进度合并刷新，慢请求不会被每条进度反复取消，采集终态会重新读取最终快照。
- 关系分层和游戏面板在接近可视区域、点击查看或通过页内链接打开时加载。关系排行由服务端搜索、筛选和分页，默认每页 30 人；环图最多展示 100 位代表玩家，选中后单独读取完整评分依据。
- Nginx 压缩 JSON、脚本和样式，SSE 保持流式传输。历史列表合并统计查询，玩家资料批量写入，采集仅维护受当前好友快照影响的连线。
- 关系评分使用有容量和时效上限的缓存，校验查询、好友快照、资料和群组版本；既有完整评分接口继续可用。

## 好友关系分层

“关系分层”是独立于游戏相关度的好友网络评分。默认以查询起点为中心，也可以通过昵称或 Steam ID 搜索切换中心。计算覆盖本次数据库保存的全部节点，不受关系图谱的显示人数、层级限制；打开、搜索和切换中心只读本地数据库，不触发 Steam 采集。

网络基础分为四项之和，各项保留一位小数：

| 依据 | 计算 | 上限 |
| --- | --- | --- |
| 直接好友 | 存在已知直接好友关系加 15 分 | 15 |
| 共同好友 | `45 × R₂ / (1 + R₂)` | 45 |
| 好友圈重合 | 两人好友集合的交集 / 并集，计算前移除彼此，乘 25 | 25 |
| 间接连接 | `15 × R₃ / (1 + R₃)` | 15 |

`R₂` 对每个共同好友累计 `1 / d`；`R₃` 对每条不重复经过玩家的三跳路径累计 `1 / (d₁ × d₂)`。`d` 取已知连接数、保存的公开好友总数和 1 三者最大值，因此好友众多的中间人贡献更低。重复边、自环以及往返同一玩家形成的伪路径不重复计分。算法采用固定权重，不会因为加入无关的孤立玩家就改变分数。

公开加入的 **Steam 群组只参与关系分层**，不改变游戏相关度。设网络基础分为 `B`，群组重合比例 `J = 共同群组数 / 双方群组并集数`，则最终分为 `round(B + (100 - B) × 10% × J, 1)`。例如网络原分 40、群组重合 50%，加 3 分，最终 43 分。群组最多提供 10 分的正向辅助加成，越接近 100 分加成越小，主要依据仍是好友网络。公开空列表、没有共同群组不扣分；未采集、不可见、失败或不完整时保留网络原分。没有已知好友路径时，加入相同群组也不会生成好友关系或综合分。该加成是产品规则，不代表实际互动或真实关系的统计概率。

在关系分层中主动采集群组，为本次已保存的所有玩家补充群组；范围不受画布显示人数限制。首次通常每位玩家需要一次公开群组网页请求，重试也计入预算；默认本次总预算 500，可设置 1–10000，达到上限后增加总预算继续。页面只读本地缓存，只有主动采集或刷新才访问 Steam。详情展示网络基础分、群组加成、快照状态/时间与最多 20 个共同群组链接，完整交集均参与评分。

群组按稳定的 Steam clan ID 匹配，保留名称、公开链接与成员数。解析必须确认完整卡片数量等于页面公开群组总数；遇到分页、不完整或结构变化时标记不可用，不把部分列表当作完整列表。成员数仅作展示，不另作权重。群组结果独立缓存并固定到本次查询的群组采集任务；另一查询的采集不会修改它。刷新失败保留旧内容，但旧内容不会当成本次可用评分依据。数据库和后台任务重启后可继续未完成的采集。

由近到远按分值分为核心层（≥60）、紧密层（35–59.9）、连接层（15–34.9）、外围层（<15）。没有已知路径的玩家单独列为“暂无已知路径”，分数为空；有路径但超过三跳的玩家可能为 0 分。圈层依据分数，与最少好友跳数是两个指标。图中展示有数量上限的代表节点，完整名单可搜索和翻页；点击玩家可查看分值构成、共同好友示例和三跳路径数量。

分数是本项目自定义的**已采集网络结构指标**，不是现实关系亲疏、交互频率或好友概率。资料私密、尚未采集、过期或节点预算截断都会影响依据；样本完整性单独展示，不把缺失资料当作不存在好友，后续补全可能使分数上升或下降。只有端点及其直接邻居的好友列表均成功、24 小时内且完整纳入本次网络时，相关证据才标为较完整。

算法参考了[共同邻居的资源分配思想](https://arxiv.org/abs/0901.0553)和[利用三跳连接的局部路径思想](https://arxiv.org/abs/0905.3558)。上述四项权重、归一化和分层阈值是本项目的产品规则，未做真实人际关系标注校准。

## 游戏相关度

在好友图谱下方的“游戏相关度”面板，点击采集按钮，比较查询起点与本次图谱中的直接好友。游戏资料单独缓存；打开面板和历史结果不会访问 Steam。手动刷新才重新采集，达到请求预算后可增加预算继续。

保持免登录、免 API：读取公开主页当前展示的近期游戏及这些游戏的**累计时长**。这通常只是少数游戏，不是完整游戏库，也不是每款游戏最近两周的时长。Steam 的完整游戏列表页若要求登录，本项目不会尝试获取登录后的数据。

评分范围 0–100，按 App ID 匹配游戏：

- 游戏重合度：共同展示的游戏数 ÷ 两人展示游戏的并集数 × 100，占 40%。
- 时长分布相似度：分别将各游戏累计时长除以本人展示游戏的总时长，再将共同游戏的较小占比相加 × 100，占 60%。
- 综合分：游戏重合度 × 40% + 时长分布相似度 × 60%，最终保留一位小数。

例如，两人展示相同的两款游戏，时长占比分别为 75%/25% 和 25%/75%，综合分为 70。总时长不同但分布相同，可以得到同样的分数；面板会另外展示时长和游戏样本数。

公开位置最多占综合分的 **5%**：双方公开了可比较的位置时，最终分 = 游戏基础分 × 95% + 位置相似度 × 5%（即游戏集合/时长/位置权重为 38%/57%/5%）。国家或地区与具体地点均相同为 100，仅国家或地区相同为 50，国家或地区不同为 0。只在能可靠识别国家后缀时比较具体地点，不从未知文本推测城市。任一位置缺失或无法比较时不启用这 5%，保留原游戏分；游戏数据不足时位置不会单独生成综合分。

分数仅代表公开样本的相似程度，不代表关系亲疏。位置是玩家自行填写的资料，不代表已验证的居住地。没有展示的游戏不代表从未玩过。游戏私密、读取失败、时长隐藏、没有游戏样本或总时长为零时显示“无法评分”，不会用零分替代。刷新失败保留旧缓存，但旧数据不会冒充本次有效评分。位置与游戏一起保存为评分快照；刷新悬停卡资料不会改写历史评分，重新评分请点击“刷新样本”。

## 头像公开资料卡

将鼠标停留在图谱头像、搜索结果、玩家详情、历史记录头像或评分排行头像上，可查看公开填写名称（`header_real_name` 中的 `bdi`）、公开位置（`header_location`）和官网“此用户也使用过以下名称”记录。键盘聚焦或手机点击头像也可打开，Escape 或关闭按钮可关闭。

悬停约 350ms 后先读数据库，仅首次查看缺失字段才采集。姓名和位置读取公开主页，曾用名读取 Steam 官网名称弹窗所用的匿名 `ajaxaliases` 请求，不使用 Steam Web API、API Key 或登录凭据。官网可能只展示有限名称记录，并允许用户清除记录，本项目不声称完整永久历史。所有值按文本显示。

公开资料和曾用名分别缓存、记录状态及采集时间。重复悬停和重新打开页面复用已保存资料，点击“刷新资料”才主动更新已采集字段；失败时保留并明确标记旧快照。游戏采集会同时缓存同一主页的姓名与位置，不增加额外主页请求。请求沿用全局限速和每日预算，同一玩家的并发悬停会合并采集。

## 服务

| 服务 | 职责 |
| --- | --- |
| web | Nginx 静态前端和 `/api` 反向代理，默认端口8080 |
| api | Fastify 查询接口、任务管理、SSE进度 |
| worker | pg-boss 持久任务队列、限速和分层采集 |
| db | PostgreSQL 16，数据存入命名卷 |
| migrate | 每次启动检查并初始化数据库，成功退出后 API 才启动 |

技术栈：React / Vite / Tailwind / shadcn 风格自有组件 / TanStack Query / G6 / ECharts / Fastify / Drizzle / PostgreSQL / pg-boss / Graphology。

```sh
docker compose ps
docker compose logs -f api worker
docker compose stop
docker compose start
docker compose down
```

`stop`、`start` 和普通 `down` 保留数据库。**`docker compose down -v` 会删除数据库卷及所有已采集数据。**

默认只监听本机 `127.0.0.1:8080`。本版面向个人使用，尚未提供登录和多人权限；需要公网部署时，应先在反向代理增加认证和 HTTPS，再更改监听地址。数据库不暴露宿主机端口。

使用示例主页进行了匿名真实两层采集，当次得到 469 个节点、499 条已知关系，重复查询复用缓存；浏览器检查无控制台错误。实际结果会随好友变更和隐私设置变化。上述验证不代表万节点图谱的性能保证。

同一主页的游戏采集使用 17 次公开主页请求，覆盖起点和 16 位直接好友：8 位可评分、8 位公开游戏样本不可访问，最高分 77.3。重新打开页面及点击使用缓存后请求数仍为 17。桌面和 390px 移动端页面已检查，分数、共同游戏时长、不可评分原因及计算说明均可查看。

资料卡版本再次刷新这 17 人的公开样本，起点未填写位置，因此游戏分保持不变。实测图谱节点和排行头像的悬停卡能显示官网名称记录及公开姓名/位置；重复打开复用相同缓存时间。浏览器检查了键盘 Enter/Escape 焦点返回、390px 触屏点击及抬手后保持显示、卡片边界和关闭操作，控制台无错误。
